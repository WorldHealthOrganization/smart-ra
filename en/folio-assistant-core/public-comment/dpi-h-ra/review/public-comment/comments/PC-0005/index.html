comment
Principle IX makes trust and security architectural properties while appropriately leaving "the specific controls, configurations, and operational practices" to implementation and national security policy (L426–427). The procurement and conformance material nevertheless supplies no common supplier-assurance baseline against which a country can evaluate how a DPI-H software component was built and how it will be maintained. Section 3.6.5 asks that requirements be testable "so that countries can validate conformance – including the claims of vendors – before and during procurement" (L955–959), and section 4.3.5 asks countries to "establish minimum conformance requirements for each DPI-H component and define the testing mechanisms through which conformance is assessed" (L400–401) – but both concern conformance to interoperability and information-model profiles. Appendix C commonly requires access control and audit logging, which are properties of the running system. Across the draft there is no occurrence of software bill of materials, vulnerability, secure development, penetration testing or end-of-support. A component can therefore satisfy its information-model and access-control requirements without the guidance asking the supplier to identify its material dependencies, state how long the version will be supported, provide a route for reporting a vulnerability, or show how a security defect reaches deployed installations as a trusted update. This is a completeness gap in the common architecture rather than a request for WHO to prescribe a national control framework, and it sits on a different axis from interoperability conformance.
